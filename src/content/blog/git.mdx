## 1. Introduction to Git

Git is a distributed version control system (DVCS) that tracks changes in source code. Every developer has a full copy of the repository with complete version history.

---

## 2. Basic Git Concepts

### **Repository (Repo)**

A collection of files tracked by Git.

### **Commit**

A snapshot of the project at a specific point in time.

### **Branch**

A separate line of development.

### **HEAD**

A pointer to the current commit.

### **Staging Area (Index)**

Where changes are prepared before committing.

---

## 3. Common Git Commands

### **Initialize & Clone**

* `git init` → Creates a new empty repository in the current folder.
* `git clone <url>` → Downloads a remote repository including full history.

  * Example: `git clone https://github.com/user/repo.git`

### **Status**

* `git status` → Shows changed, staged, and untracked files.

### **Staging Files**

* `git add <file>` → Stage a specific file.
* `git add .` → Stage all modified and new files.
* `git restore --staged <file>` → Remove a file from staging.

### **Committing**

* `git commit -m "message"` → Create a new commit.
* `git commit -am "message"` → Add tracked files & commit them in one step.

### **Branching**

* `git branch` → List branches.
* `git branch <name>` → Create a new branch.
* `git switch <name>` → Switch to a branch.
* `git switch -c <name>` → Create and switch to a branch.

### **Merging**

* `git merge <branch>` → Merge another branch into the current one.
* Resolves differences using three-way merge.

### **Rebasing**

* `git rebase <branch>` → Replay commits on top of another branch.
* `git rebase -i <commit>` → Interactive rebase for squashing and editing commits.

### **Fetching vs Pulling**

* `git fetch` → Downloads commits and updates remote-tracking branches.
* `git pull` → Fetch + merge.
* `git pull --rebase` → Fetch + rebase instead of merge.

### **Remote Management**

* `git remote -v` → Show remotes.
* `git remote add origin <url>` → Add a new remote.
* `git push origin <branch>` → Push branch.
* `git push -u origin <branch>` → Push and set upstream.

### **Resetting**

* `git reset --soft <commit>` → Roll back commit but keep changes staged.
* `git reset --mixed <commit>` → Default; keep changes unstaged.
* `git reset --hard <commit>` → Discard all changes and commits.

### **Reverting**

* `git revert <commit>` → Create a new commit that undoes a previous commit.

### **Stashing**

* `git stash` → Save uncommitted work.
* `git stash list` → Show all stashes.
* `git stash apply` → Restore last stash.
* `git stash pop` → Restore + remove stash.

### **Logs & History**

* `git log` → Full commit history.
* `git log --oneline` → Short, readable format.
* `git log --graph --decorate --all` → Visual graph.

### **Diff**

* `git diff` → Show unstaged changes.
* `git diff --staged` → Show staged changes.
* `git diff <branch1> <branch2>` → Compare branches.

### **Tagging**

* `git tag <name>` → Create a tag.
* `git tag -a <name> -m "message"` → Annotated tag.
* `git push origin <tag>` → Push tag.
* `git push --tags` → Push all tags.

### **Cherry-Pick**

* `git cherry-pick <commit>` → Apply an existing commit onto current branch.

### **Cleaning**

* `git clean -n` → Preview files to be removed.
* `git clean -f` → Remove untracked files.

### **Bisect**

* `git bisect start` → Begin binary search for bug.
* `git bisect good` / `git bisect bad` → Mark commits.
* `git bisect reset` → End the bisect session.

## 4. Merge vs Rebase

### **Merge**

* Creates a merge commit.
* History shows all branches.
* Useful for preserving context.

### **Rebase**

* Rewrites commit history.
* Makes a clean, linear history.
* Best for local branches before pushing.

---

## 5. Merge Base

### **Definition**

`merge-base` is the **common ancestor** between two branches.
Git uses this commit as the reference point during merging.

Example:

```
git merge-base main feature/login
```


This returns the commit hash of the shared ancestor.

### **Why it's important?**

* Git compares branch changes since the merge-base.
* Helps avoid unnecessary conflicts.
* Used internally for `merge`, `rebase`, and `diff`.

---

## 6. Fast-Forward vs Non–Fast-Forward

### **Fast-Forward Merge**

Occurs when the target branch has not diverged.

```
A -- B -- C (main)
          \
           D -- E (feature)
```


`main` simply moves forward to E.

### **Non–Fast-Forward Merge**

Occurs when branches diverge, producing a merge commit.

---

## 7. Git Three-Way Merge

Git compares:

1. The **merge base**
2. The **source branch**
3. The **target branch**

and resolves differences.

---

## 8. Git Conflicts

Conflicts occur when two branches modify the same lines.
Git marks them with:

```
<<<<<<< HEAD
Current branch
=======
Incoming branch
>>>>>>> feature
```


Developer must manually resolve.

---

## 9. Git Reset vs Revert

### **Reset**

Moves HEAD to a previous commit.

* `--soft` → keep changes staged
* `--mixed` → keep changes in working dir
* `--hard` → delete changes

### **Revert**

Creates a new commit that undoes changes.

* Safe for public branches.

---

## 10. Git Cherry-Pick

```

```


Useful in hotfix scenarios.

## 13. Git Hooks

Scripts that run automatically at key Git events:

* pre-commit
* pre-push
* commit-msg
  Useful for code formatting, linting, etc.

## 14. Git Workflows

### **Git Flow**

* `main` (production)
* `develop`
* feature branches
* release branches
* hotfix

### **GitHub Flow**

* `main`
* feature branch → PR → merge → deploy

### **Trunk-Based Development**

* Very small branches
* Frequent merges

---

## 15. Git Pull vs Fetch

### **git fetch**

Downloads remote changes **without merging**.

### **git pull**

Equivalent to: `git fetch` + `git merge`.

---

## 16. Advanced Topics

### **Reflog**

Tracks movements of HEAD.
Useful for recovering lost commits.

```
git reflog
```


### **Squash Commits**

```
git rebase -i HEAD~5
```


Combine several commits into one.

### **Sparse Checkout**

Checkout only parts of a repo.

---

## 17. Best Practices

* Commit frequently with clear messages.
* Avoid rewriting history on shared branches.
* Use branches for features.
* Protect `main` with PR reviews.
* Use `.gitignore` wisely.
