# 1. Introduction

Security is a crucial part of any mobile application. iOS provides strong built-in protections, but developers must still follow best practices to prevent data leaks, unauthorized access, reverse engineering, and network attacks.

This guide explains **how to make your iOS app more secure** using Swift, system APIs, and architectural decisions.

---

# 2. Secure Storage

Sensitive data should **never** be stored in UserDefaults, files, or Core Data without protection.

## 2.1 Keychain

The most secure place for:

* Tokens (JWT, OAuth)
* Passwords
* Refresh tokens
* API keys (if unavoidable)

### Why Keychain?

* Hardware encrypted
* Protected by device biometrics
* Persist across app reinstalls (optional)

### Best Practices

* Store the minimum amount of data
* Use `kSecAttrAccessibleAfterFirstUnlock` for background operations
* Never store plaintext tokens

---

# 3. Secure Network Communication

Networking is a major attack vector.

## 3.1 Enforce HTTPS

Enable **App Transport Security (ATS)** by default.

## 3.2 SSL Pinning

Prevents man-in-the-middle (MITM) attacks.
Use:

* **URLSession + Trust Evaluation**
* **Alamofire SecurityPolicy**

Pin:

* Certificate
* Public key

## 3.3 Avoid Exposing API Keys

Never hardcode keys. If needed:

* Use Keychain
* Retrieve from backend when required
* Use Apple’s DeviceCheck / App Attest

---

# 4. Secure Coding Practices

## 4.1 Avoid Force Unwrapping

Crash = easier attack surface.

## 4.2 Avoid Using Sensitive Data in Logs

Never log:

* Tokens
* Passwords
* User personal data

Use OSLog with privacy masking:

```swift
logger.log("Token: \(token, privacy: .private)")
```


## 4.3 Use `final` classes and `private` members

Prevents unwanted subclassing or misuse.

---

# 5. Data Protection on Disk

Enable file protection for anything stored on disk.

```swift
try data.write(to: url, options: .completeFileProtection)
```


Protection levels:

* completeFileProtection
* fileProtectionCompleteUntilFirstUserAuthentication

Applies to:

* Local JSON cache
* Images
* Database files

---

# 6. Securing Local Databases

## 6.1 Core Data

Encrypt SQLite manually if needed.

## 6.2 Realm

Realm supports built-in AES-256 encryption.

```swift
let config = Realm.Configuration(encryptionKey: key)
```


## 6.3 SwiftData

Backed by Core Data → same file protections apply.

---

# 7. Authentication & Authorization

## 7.1 Biometrics (Face ID / Touch ID)

Use for unlocking sensitive parts of app.

```swift
LAContext().evaluatePolicy(.deviceOwnerAuthentication)
```


## 7.2 OAuth2 / JWT

* Use short-lived access tokens.
* Refresh tokens stored only in Keychain.

## 7.3 DeviceCheck & App Attest

Protect server APIs from unauthorized or spoofed apps.

---

# 8. Reverse Engineering Protection

Attackers may try to inspect, modify, or pirate your app.

## 8.1 Obfuscation

Use Swift Obfuscator tools to scramble:

* Class names
* Method names
* Strings

## 8.2 Remove Sensitive Strings

Avoid embedding:

* Hidden URLs
* Admin keys
* Secrets

---

# 9. Secure Architecture Principles

## 9.1 Never Trust the Client

All validation must be on the backend.

## 9.2 Use Zero-Trust Token Policies

* Short-lived JWTs
* Rotate tokens regularly

## 9.3 Validate All Input

Always validate:

* API responses
* User input
* JSON types

---

# 10. Protect Against Common Threats

## 10.1 Jailbreak Detection

Basic detection (not 100% secure):

* Check for known jailbreak file paths
* sandbox directory write validation

## 10.2 Replay Attacks

Use

* Nonces
* Timestamps
* HMAC signatures

## 10.3 Brute-force Attacks

Limit retries for sensitive actions.

---

# 11. API Security

## 11.1 Rate Limiting

Prevent brute-force API abuse.

## 11.2 HMAC Signatures

Server generates a signature using a shared secret.
App sends:

* timestamp
* payload
* HMAC hash

Prevents: tampering, replay, injection.

---

# 12. Secure Push Notifications

Never send:

* Tokens
* Personal data
* Password reset codes

Use silent push for sensitive operations.

---

# 13. Secure User Defaults

Never store sensitive data.
Use only for:

* simple flags
* cached state
* UI preferences

---

# 14. Secure SwiftUI Practices

## 14.1 Avoid Putting Sensitive Data in State

State variables are stored in memory and can be inspected.

Use Keychain for sensitive data.

## 14.2 Avoid Passing Sensitive Data Through Bindings

Binding chains can expose data.

---

# 15. Testing & Auditing

## 15.1 Security Testing Tools

* MobSF
* OWASP MASVS
* Xcode memory debugger

## 15.2 Penetration Testing

Use tools to test:

* MITM attacks
* API injection
* Certificate pinning bypass

---

# 16. OWASP Mobile Top 10 Mapping

Examples:

* M1: Improper Platform Usage → Keychain misuse
* M4: Insecure Authentication → weak tokens
* M5: Insufficient Cryptography → no encryption
* M10: Extraneous Functionality → debug logs

---

# 17. Summary

To make an iOS app more secure:

* Use Keychain for sensitive data.
* Enforce HTTPS + SSL pinning.
* Avoid logging sensitive info.
* Protect local storage with file protection.
* Use biometrics for sensitive screens.
* Avoid hardcoding secrets.
* Validate everything server-side.
* Follow OWASP and iOS best practices.
